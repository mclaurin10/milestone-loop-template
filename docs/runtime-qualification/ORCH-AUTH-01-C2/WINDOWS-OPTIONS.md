# Native Windows execution options — C2 investigation

Observed 2026-09-06 UTC. These are feasibility findings, not qualified execution. The new native metadata observation again identifies Windows 11 Pro build 26200 with no discovered Docker, Podman, Hyper-V management, QEMU, VirtualBox or Windows Sandbox launcher. No provider, service, feature or VM was installed on Windows. This is a bounded command search, not an exhaustive inventory. Server 2022 is not the inspected workstation.

| Route | Vendor-documented scope | Repository gap and disposition |
| --- | --- | --- |
| Dedicated supported Windows client with Docker Desktop and its Linux backend | Docker supports suitable Windows 10/11 client systems. Desktop excludes Windows Server 2019/2022. | Most direct native Windows controller route to investigate. Requires an authorized isolated machine lifecycle, exact native Node/pnpm, immutable OCI image and actual public-workflow/containment evidence. No host exists here; NOT_READY. |
| Windows client VM/VDI with Docker Desktop | Docker's nested-virtualization support states Docker Business with VMware ESXi or Azure VMs. Its current VDI guidance excludes non-persistent environments that reset the OS and require reinstallation/reconfiguration each session. | Do not assume an arbitrary local Hyper-V/QEMU VM or disposable VDI snapshot is vendor-supported. Establish the exact host/lifecycle support before provisioning; no subscription, VM or external service was used. NOT_READY. |
| Native Windows process with a separate Linux Docker daemon | Docker documents SSH/TLS daemon access, but daemon bind mounts address the daemon filesystem. | Existing executor supplies local absolute source/store paths and validates the exact applied mount set. It has no authenticated source/store transport and path-mapping adapter for this route. An arbitrary context or CLI shim cannot satisfy those checks. NOT_READY. |
| Docker Offload | Docker documents Desktop integration with cloud execution and bind-mount forwarding when nested virtualization is unavailable. | A documented commercial route, not an authorization, supported provider attestation or proven fit for this executor's exact filesystem/network/resource inspection. Credentials, support/lifecycle scope and real policy evidence would be required. No connection or purchase was attempted. NOT_READY. |
| Server 2022 Windows container runtime or LCOW | Microsoft supports Windows Server containers on Server 2022; its support article says LCOW on Server is deprecated. | The existing trusted image, Linux entrypoint, UID, tmpfs and resource/mount assertions are Linux-specific. Installing a Windows daemon cannot qualify that provider. Server 2022 reference remains unresolved and is not replaced. |
| Controller inside WSL | Microsoft documents WSL installation on Windows Server, including Server 2022. | That controller is a Linux process. It can only supply Linux evidence, irrespective of the outer Windows edition. It cannot fill the native Windows row. |

References inspected: [Docker Windows installation](https://docs.docker.com/desktop/setup/install/windows-install/), [Docker VM/VDI support and Offload](https://docs.docker.com/desktop/setup/vm-vdi/), [Docker bind mounts](https://docs.docker.com/engine/storage/bind-mounts/), [Docker SSH/TLS daemon access](https://docs.docker.com/engine/security/protect-access/), [Microsoft Windows container support](https://learn.microsoft.com/en-us/troubleshoot/windows-server/containers/support-for-windows-containers-docker-on-premises-scenarios), [WSL on Windows Server](https://learn.microsoft.com/en-us/windows/wsl/install-on-server).

The repository-specific conclusions are code inspection: `container-executor.ts` constructs the fixed read-only `/source` and `/pnpm-store/v11` mounts and compares their exact sources against Docker inspection, plus a Linux `/bin/sh` entrypoint, numeric user, Linux tmpfs and denied-network policy. `execution-provider.ts` currently resolves a Docker executable by name and queries its runtime/image. C2 changes neither. A future provider setup must inspect that resolved launcher as data before capability queries and must not promote a metadata discovery receipt into host authorization.

The selected C2 experiment uses an offline Linux diagnostic guest under unprivileged QEMU TCG. It establishes none of these Windows routes. Continue native Windows qualification as a distinct unfinished requirement; preserve Server 2022, all original gates and settled r2 authority.
