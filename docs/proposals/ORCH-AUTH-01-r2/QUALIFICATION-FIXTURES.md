# Exact fixture outcomes and limits

This is advisory ORCH-AUTH-01 fixture design. The normative acceptance manifest and bounded target contract own the required consumer outcomes and claim limits; this document describes their proposed implementation without creating requirements for an existing downstream product.

## Release/adopter bootstrap fixture

Use the existing `fixtures/fresh-adopter/definition.json` and its supplied authority bytes unchanged as the first definition. Prepare the second by changing only project/package identifiers, Git identity/timestamp and target branch through the existing definition fields; use a destination containing spaces. Do not change its acceptance to make the smoke pass. Run the actual documented create/install/commission/commit/verify/prove path from the extracted release. Inspect real build output, Node/replay/Worker continuation, saved state and browser artifacts. Bootstrap results remain generated-adopter bootstrap evidence and explicitly completion-ineligible for product readiness.

## Bounded orchestration target fixture

Production controller lifecycle qualification needs a valid target contract independent of the source's self-qualification. Use a disposable target whose complete declared product is a versioned message-file CLI: `message.json` contains exactly one string field named `message`; `message.mjs show` prints that string followed by one newline; `message.mjs set <value>` validates a nonempty UTF-8 string of at most 128 bytes and publishes a canonical JSON record atomically. Initial value is `initial`; a bounded milestone changes its default to `reviewed`. A corrupt JSON file or invalid value must fail without overwriting prior bytes. Build copies the CLI and validated default data to a fresh distribution directory, and the built CLI is exercised from outside the checkout. This product has no browser, game, bots or random seed semantics. The exact proposed [bounded contract](proposed/qualification-target-contract.json) enumerates its outcomes and claim limits.

The fixture's explicitly frozen contract must require exact runtime/dependencies, real clean build and external CLI use, correct accepted/rejected mutation behavior, byte-identical state continuation after restart, and owned receipts; no placeholder script or invented PASS is permitted. Its scoped verification registry is a normal commissioned target contract accepted by the same production readers and handlers. Scope is fixed by the target's independently anchored authority before worker invocation, not selected by a worker flag or the source candidate. New support for this versioned bounded-target contract, including strict result/schema validation, is required harness implementation; it is not claimed to exist today.

This is a source-qualification fixture scope, not source release or arbitrary downstream completion. Its report identifies that fixture's authority and exact candidate separately. The controller still enforces the same protected roots, standalone clone, trusted provider, owned evidence, review independence, freshness, lease/state/intent and fast-forward rules. There is no fixture exception for eligibility or integration safety. Cross-scope tests must prove that neither a message-fixture PASS nor an adopter bootstrap PASS can satisfy the source or an unrelated downstream gate. Original legacy downstream contracts remain accepted unchanged; no fixture rewrites an old BOT/SEED requirement.

The deterministic Planner supplies a real bounded proposal. The Worker subprocess edits permitted fixture source files. The independent Reviewer subprocess reads the actual diff, verified candidate and expected outcomes, and returns a bound structured decision; it does not merely echo a worker decision. The real controller handles everything else. Driver-owned state construction is limited to ordinary initialization and the deliberate external/mutation inputs specified by a scenario; it must not manufacture the operation's resulting state or refs. Reconciliation/retention approvals belong to separate maintainer fixture actors and are bound to their exact disposable target/plan.

Human acceptance uses the same declared small product outcome with the live configured agent transport and explicit operator acceptance. Its success demonstrates the product's live supported lifecycle for that requirement, not general coding capability. The acceptance of this fixture design does not authorize changing an existing adopter's authority.

## Failure variants

Each of the sixteen named families expands to every relevant current publication boundary and rejected identity/state variant from the existing regression corpus. Examples must include before and after ref publication, before and after canonical state publication, before and after filesystem replacement, lease ownership change, receipt omitted despite exit zero, mismatched source/fixture hashes, and foreign path/ref insertion while an intent is pending. The implemented fault-point registry is audited against production mutation sites and stored in the report; new unregistered sites fail discovery. This is a mandatory completeness rule, not permission to select one easy variant per family.
