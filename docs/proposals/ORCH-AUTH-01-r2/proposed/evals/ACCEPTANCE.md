# Source Orchestrator/Template Acceptance

Contract: `milestone-loop-orchestrator-source.v1`. Authority epoch: `orch-template.v1`. Claim scope: `orchestrator-template`. The machine-readable twin is `evals/acceptance-manifest.json`.

## Evidence rules and gates

Every required observation is tied to the exact source commit/tree, authority/lock/manifest hashes, run ID, platform, runtime, command argv, and execution-provider identity. Workflow evidence separately identifies the disposable fixture/adopter commit and authority; those identities must never be substituted for the source identity. Every successful child command owns a validated receipt with nonempty required artifacts, sizes, and SHA-256 hashes. Verification independently checks those artifacts and the actual before/after Git, state, process, and filesystem observations. Exit zero, a unit-test report, a self-asserted status, or a fabricated sandbox identity is insufficient.

The public command handlers and shared production controller perform all transitions. Workflow drivers may set up fresh repositories and supply deterministic, separately executed role responses. They must not seed a completed state, mutate private refs as the supposed operation, generate fake child receipts, accept a review on the worker's behalf, or override isolation/eligibility guards. Each scenario reports whether its role transport is deterministic or live. Unit/regression tests remain mandatory supporting evidence but cannot replace the workflow observations below.

`ORCH-AUTONOMOUS-READINESS-01` requires all twelve machine requirements, all metrics, all sixteen negative scenarios, both supported platforms, the exact no-argument source verification gate, and no identity/authority drift. Source artifact eligibility is scoped to this source contract only. Missing, unavailable, skipped, flaky, timed-out, or mismatched evidence remains non-passing. An expected rejection is a successful negative scenario only when the intended boundary actually executes, rejects for the specified reason, and leaves the specified state intact; an earlier missing-runtime failure cannot satisfy it.

`ORCH-HUMAN-ACCEPT-01` follows machine readiness and requires the live operator workflow below. All gates use logical AND without averaging or compensation. No migration or proposal-integrity report is a product acceptance receipt.


## Candidate and full-qualification cadence

The manifest verificationCadence is normative. Iteration executes canonical invariants and explicit focused checks. Candidate verification executes invariants first, dependency/static/architecture/type checks, one real payload build with bounded external executable smoke, and every canonical owner partition once. Add explicit production workflow cases for affected behavior, with changed-path rationale, actual platform/provider and coverage. Unresolved required coverage fails broad or stays unsupported. Do not suppress existing mandatory tests.

Candidate/iteration/supporting results remain completion-ineligible. They do not automatically dispatch all domains/fault variants, the complete native-platform matrix, repeated builds, cross-platform parity or both complete adopter definitions. No such result can replace full readiness or authorize an integration/reconciliation that requires exact closure. This is not a new profile or scope-suppression graduation.

Full qualification remains one fresh literal no-argument source pnpm verify invocation, required for milestone/periodic exact closure and any operation demanding full exact readiness. Every final outcome, metric, failure variant, both native platforms and separate human gate remains mandatory. No old same-commit or candidate receipts can satisfy fresh closure.

Record dispatch purpose, cases, platform, producer count and justification before execution, and observed cost afterward. Multiple consumers of one immutable producer result within the fresh invocation do not require duplicate dispatch. Distinct mandatory repeated observations still execute independently. The existing five protected CI jobs and bounds remain unchanged; no automatic per-commit full release trigger is added.

## Production release build

The release is an allowlisted runtime/template distribution, not a copy of the working tree. Its payload contains the public CLI runtime (including the generator), schemas, configuration templates, bootstrap scaffold, necessary tools, package/workspace manifests, frozen lockfile, notices and user instructions. Preserve the currently supported TypeScript/tsx runtime layout; a new compiled SDK or npm publishing system is not required. Tests are packaged only where the installed controller, invariant/ownership discovery, generated verification or qualification workflow requires them; dependencies and runtime entrypoint discovery must prove the allowlist is complete.

The declared production build emits a portable payload, deterministic archive and release manifest under safe declared output roots. The current dist layout and internal build-script wiring are implementation notes, not frozen authority. The manifest identifies the source commit/tree and each payload file's path, bytes, and hash. Source identity metadata is fixed for identical input commits; wall-clock build telemetry is outside the reproducible payload. No credentials, source `.git`, controller state, workspaces, evidence caches, source readiness marker, source commissioning state or source acceptance identity may leak into a generated adopter. The release's own provenance remains distinguishable from that adopter's identity.

The archive is safely extracted into a fresh absent path, dependencies are installed from the frozen lock, and the extracted CLI is the only runtime used for the generation smoke. No source-checkout imports or writable shared node_modules are permitted. Repeated builds start with absent output roots and independent writable workspaces. The portable payload inventory must also agree between Windows and Linux; platform-specific dependency installations and execution telemetry are recorded outside that payload. Removing a declared runtime/schema/scaffold file from a committed mutation must break the external smoke. Full ORCH-BUILD-01 success requires the payload and complete real consumer observations. Ordinary candidate build evidence covers one actual payload and bounded external executable smoke, is explicitly incomplete for ORCH-BUILD-01, and cannot claim repeated-build or full generation/commissioning coverage.

## Qualification invocation and recursion boundary

One literal no-argument source `pnpm verify` invocation owns a fresh cross-platform qualification identity and all required stages. A trusted external coordinator dispatches native Windows/Linux jobs for the full required observation matrix and validates their provenance and artifacts. Those jobs execute the source stage commands and real controller workflows; they do not recursively request source readiness. Generated adopters and bounded target fixtures execute their own distinct contracts. The source result cannot become completion-eligible until every required platform/provider observation has been independently validated.

The tested controller needs a container control plane, so it runs on a maintainer-authorized disposable qualification host. Its candidate children remain in the existing attested OCI sandbox. Source candidate commands inside that sandbox cannot launch Docker or contact a qualification service. Where a source tier consumes remote workflow observations, the trusted outer coordinator must first produce a fresh, nonce-bound bundle of exactly its declared supporting or full-qualification purpose and case coverage and deliver it through a validated read-only task-input channel. The child command independently checks that bundle and owns a receipt for that verification; producer-owned workflow receipts remain separately retained. The outer verifier independently checks both. Candidate-authored files cannot act as coordinator approval or provider attestation. Missing coordinator, input-channel support or provenance remains NOT_READY, never host fallback. Candidate support dispatches only its declared focused cases on the required qualified host; it does not automatically request the full release matrix. The full gate independently rejects supporting or incomplete coverage. QUALIFICATION-PROTOCOL.md is advisory implementation guidance; these provenance, containment, freshness and completeness boundaries remain normative.

## Required negative scenarios

The manifest names exactly sixteen scenario families, each mandatory on Windows and Linux. Each uses a real subprocess/command boundary and records its complete variant list: invalid proposal; protected-worker write; unclassified test; missing/forged child evidence; stale/rejected independent review; target divergence; stale/corrupt state; competing lease/generation; workspace-create crash; candidate-prepare crash; integration crash; cleanup escape/crash; unapproved/stale retention; external-reconciliation mismatch; amendment mixed/foreign/crashed generation; containment/supervision violation. Multi-boundary variants within a family all must pass; one representative cannot replace an omitted boundary.

Required rate is 16/16 correct family dispositions and 100% of enumerated variants on each platform, with zero unexpected integrity violations. A deliberately rejected operation is not itself an integrity violation. Skips and infrastructure failures are not correct negative outcomes. This finite corpus is qualification evidence, not a 99% reliability estimate.

## Human and live-agent acceptance

After machine qualification, the maintainer uses the delivered distribution to create and commission a disposable adopter with a bounded real requirement and actual acceptance assertions. Use the committed live agent/model policy with separate Planner, Worker and Reviewer sessions. Exercise a successful change through verification, independent review and fast-forward integration; deliberately reject a stale/rejected candidate; terminate and resume one operation; inspect Status/Doctor and the evidence chain. Record actual transport and role identity, source release/adopter identities, commands, artifacts, review and maintainer disposition. Never substitute deterministic adapter output or scripted unit success for this live workflow.

The maintainer verifies that instructions are sufficient, the integrated outcome meets the fixture's stated requirement, failed paths preserve data, and claim labels are understandable. Approval must be explicit and bound to the release digest. Missing credentials or service access leaves this gate pending. Human acceptance establishes the supported operator workflow, not arbitrary coding quality or downstream product completion.
